## 四、已经踩过的坑，别再踩

### (1) xorbitsai 不可用 —— 不是环境问题，是结构冲突

探了 17 条只过 1 条（6%）。9 条「gold 没修好」逐条查过，**8/8 都是同一个病**：

| PR | 挂掉的用例 | 为什么必挂 |
|:---|:---|:---|
| 2540 | `test_convert_ids_to_tokens` | 下 embedding 模型 |
| 2738 | `test_model_error` | 要起服务 |
| 2790 / 2843 | `test_kokoro` / `test_kokoro_zh` | 下 Kokoro TTS 模型 |
| 3442 | `test_gguf_multimodal` | 下 GGUF 模型文件 |
| 3658 | `test_builtin_families` | 要起 REST 服务 |
| 3768 | `test_qwen3_with_thinking_params` ×6 + `test_qwen3_with_tools` | 下 Qwen3 |
| 3794 | `test_qwen3_enable_thinking` ×4 | 下 Qwen3 |

源码长这样：

```python
async def test_qwen3_enable_thinking(setup_cluster, ..., engine):
    endpoint, _ = setup_cluster                # 起一个真的推理集群
    client.launch_model(model_name="qwen3")    # 下载 Qwen3（几个 GB）
    if engine == "vLLM":
        torch.cuda.get_device_properties(0)    # 还要 GPU
```

**沙箱必须断网**（协议 C-31 / C-35【必须】），否则被测 AI 能直接去 GitHub 抄补丁。
所以「给沙箱开网」不是解法 —— 开了基准就作废了。

**推论**：中文 issue 多的活跃 Python 项目绝大多数是 AI 基础设施，
而 AI 基础设施的测试与断网要求存在结构性冲突。这条因果链是 E1-T8 那张卡的立卡理由，
也是报告里必须主动披露的降级原因。

### (2) 一个仓库一个镜像，只能服务依赖兼容的那一段 `base_commit`

tortoise-orm 探了 10 条，结果按 `base_commit` 年份整齐分层：

| 年份 | 探了 | 通过 | 挂在哪 |
|:---|---:|---:|:---|
| 2026 | 5 | **4（80%）** | — |
| 2025 | 3 | 0 | 跑得起来，但新加的测试在报告里找不到 |
| 2024 | 3 | 0 | `ModuleNotFoundError: No module named 'pypika'`，一条用例都收集不到 |

2024 段挖到底分两层：

1. **缺包**（能修）：装 `pypika` + `pyodbc` + `asyncodbc` + 系统库 `unixodbc`
   之后，**1196 条用例全部收集成功、0 错误**
2. **版本对不上**（修不了）：收集成功之后跑起来 **1196 条全部 ERROR**，
   `AttributeError: 'Connection' object has no attribute 'start'`
   —— 2024 年的 tortoise 调的是老版 aiosqlite 的 API，镜像装的是 2026 年的

**教训：「用例能收集到」不等于「题能出得来」。** sqlfluff 现在正卡在这个状态：
补上 `appdirs` 之后能收集到 8149 条，但**从没验过 gold 补丁真能把测试修好**。

**click 的 86% 探测通过率是特例，不是基准** —— 它几乎没有依赖，
所以两年间的代码都能在同一个环境里跑。任何有真实依赖的仓库都会低得多。

### (3) sqlfluff 的两个硬阻塞（配方里也写了）

1. **全量套件 606–663 秒**（8152 条用例，2 CPU），超过题目默认的 `test_timeout_s=480`。
   探测那侧已经加了 `--suite-timeout`（默认 1800），**正式评测不受影响**
   —— 那时 P2P 按 §7.7 走 `module_and_random` 子集
2. **内存峰值 1.885 GiB**，沙箱默认上限 1536 MB，差 0.39 GiB，探测直接 `OOM_KILLED`。
   要 2.5 GB 才有余量，但那撞上 E9-T2 定档的 `sandbox=4`（4×2.5=10 GB vs 本机 11.7 GB）。
   **这不是机器内存不够**（现在 8.6 GB 空闲），是并发档位和单容器上限的取舍，
   三选一：跑 sqlfluff 时并发降到 3 / 只给 sqlfluff 的题单独设 2.5 GB（要改容量模型）/ 不用它

### (4) 候选池深度 ≠ 出题能力

sqlfluff 候选池 676 是全场最深，但只有 **70 条（10.4%）抽得出候选 F2P**，全场最差。
674 份测试补丁里只有 69 份（10.2%）加了 Python 测试函数，
**582 份（86.4%）改动全在 `test/fixtures/` 下**，只是 `.sql` 语料 + `.yml` 期望输出。
它是 SQL linter，修 bug 不写测试函数 —— 而 F2P 要的是**用例名**。

这条已经写进 `03-benchmark-spec.md` §8.3 的选型准则（新增一行，门槛 50%），
证据和 8 个仓库的对照表在 §8.8 最后一节。

### (5) 其他要知道的

- **探测失败的候选现在会记下挂掉的用例名**了（`raw_payload.probe.excluded`，
  2026-09-14 改的）。以前只记条数，想知道是哪几条得重跑两个容器
- **`xorbitsai/inference` 直接 clone 会断**（HTTP/2 CANCEL / early EOF / GnuTLS）。
  用 `git clone --bare --shallow-since="2.5 years ago"` 拿 2094 个提交、86 MB，
  缺的 `base_commit` 再 `git fetch --depth 1 origin <sha>` 单补
- **DeepSeek 的 Key 会欠费**。余额 0 的表现是调用全部返回 `Insufficient Balance`，
  而平台会记成 `AGENT_RUNTIME_ERROR`，看起来像被测 AI 自己挂了（issue #96 在跟）
- **一台机器同时只跑一个 Worker**，第二个 Worker 的孤儿回收会杀掉第一个的容器
- **挖掘/探测跑着的时候别裸跑 `uv run pytest tests/integration/...`**，会清开发库；
  `make test` 是安全的

| 指标 | 达标 | 降级达标 | 现在什么情况 |

破了不等于项目失败 —— 验收表第四列写的是「**出具漏斗数据说明产出率**」，
下面紧跟一条纪律：

> 任何降级都必须在报告中**主动披露**，附数据与原因。
> 评测平台的核心品格是诚实 —— **隐瞒降级比降级本身严重得多**。

今天查出来的因果链和逐条证据（第四节）**就是这份说明的材料**。
它回答的不是「我们没做到」，而是「为什么做不到」，这是有数据支撑的真实发现。
