# 4 Feasibility Assessment（可行性分析）

逐条审查学校提的 8 个高风险要求。**原则：一条都不删，但每条都要想好"做不到的话退到哪一步还算合格"。**

## 4.1 100 道题

**能做到吗：中等把握。** 卡点不是"能不能爬到"，而是"验证得过来吗"。

每道候选题都要在 Docker 里跑两遍测试才能确认可用，一遍确认修复前测试确实失败，一遍确认打上官方补丁后确实通过。一遍 3~10 分钟。

按 SWE-Bench 公开的比例估算，各环节的通过率大概是：

```
候选 PR（关联了 issue + 改了测试文件 + 已合并）
   → 能拆出代码改动和测试改动              约 60%
   → 环境能装起来、测试能跑                约 35%
   → 修复前确实失败、修复后确实通过         约 50%
   → 测试稳定，跑两遍结果一致               约 80%

限定在精选仓库里，最终成功率 ≈ 0.6 × 0.35 × 0.5 × 0.8 ≈ 8.4%
不限定仓库、漫无目的地爬，会掉到 1~3%
```

要 100 道题，就得筛 **1200 个精选仓库的候选**，或者 3000~10000 个泛化候选。即使 8 路并行，1200 × 6 分钟 ÷ 8 ≈ **15 小时纯机器时间**，还不算失败重试和镜像构建。

- **主方案**：收敛到 **8~15 个精选仓库**（Python 为主、用 pytest、依赖轻、测试跑得快、issue 里中文多），按仓库预建镜像。挖掘从第一周第三天开始，常驻后台跑。目标自建 **60~70 道**。
- **备用方案**：不够 100 道时，用 **SWE-bench Verified 官方题目**（官方数据 + 官方镜像，转成同一格式导入）补齐，并在数据集页面标明来源构成。**这不是凑数——它同时服务于 §4.5 那个指标。**
- **底线**：平台里总共 ≥100 道可评测的题，其中自建中文题 ≥40 道。低于这条线就在报告里如实说明，并附上上面那张漏斗数据。

## 4.2 GitHub 自动挖掘

**能做到吗：部分能自动，全自动不行。**

| 步骤 | 自动化程度 | 说明 |
|:---|:---|:---|
| 搜索已合并的 PR、找到关联的 issue | **全自动** | 用 GitHub 的 GraphQL 接口，靠 `closes #123` 这类关键字匹配 |
| 把改动拆成"代码改动"和"测试改动" | **全自动** | 按路径规则分（`tests/`、`test_*.py` 之类） |
| 推断怎么装环境、怎么跑测试 | **半自动** | 从 CI 配置和 `pyproject.toml` 猜，每个仓库人工确认一次 |
| 找出哪些测试是"修复后才通过"的 | **全自动，但要实测验证** | 先从测试改动里提取候选，再靠实际跑一遍来证伪 |
| 找出"本来就该通过、不能改坏"的测试 | **全自动** | 修复前就通过、修复后仍通过的用例 |
| 判断 issue 描述够不够定位问题 | **要人工，大模型只能辅助** | SWE-bench Verified 全靠人工。我们用大模型预筛 + 人工终审 |
| 判断有没有泄题（issue 里直接贴了修复代码或 PR 链接） | **规则 + 人工** | 必须剔除，否则解决率虚高 |

所以设计一条候选流水线：`发现 → 候选 → 验证中 → 通过 / 不通过 / 需人工复核`。人工只在两处介入：需人工复核的题目、以及每个仓库第一次接入时。目标是每道题人工不超过 3 分钟。

## 4.3 接入 3 个以上被测 AI

**能做到吗：把握较大。** 关键在接入顺序（详见 §9.4）。

- **主方案**：Aider（最好自动化，第一个接）→ Claude Code（学校点名要的）→ 国产命令行工具 → 自研的简易 Agent。
- **备用方案**：如果某个商业工具卡在鉴权或容器化上，就用**自研 Agent 换不同的底层模型**（DeepSeek / Qwen / GLM）凑够 3 个"参赛者"。这仍然满足"3 个以上 AI 对比"，只是主流工具少了一个，需要在报告里说明。
- **底线**：Mock + 2 个真实 AI，其中至少 1 个是主流工具。

## 4.4 跑 300 次真实评测

**能做到吗：中等。主要限制是钱和限流，不是技术。**

单次真实仓库任务的花费估算：

| 被测 AI | 大概消耗 | 单价假设 | 单次 | ×100 题 |
|:---|:---|:---|:---|:---|
| Claude Code（按 API 计费） | 输入 15~80 万 token，输出 1~4 万 | $3/百万输入，$15/百万输出 | **$0.6~2.9** | **$60~290** |
| Claude Code（订阅制） | 同上 | 包月 | 边际成本约 0 | 但受**并发和额度限制** |
| Aider + 国产模型 | 输入 8~30 万 token | 约 $0.15~0.6/百万 | **$0.02~0.2** | **$2~20** |
| 自研 Agent + 国产模型 | 输入 6~20 万 token | 同上 | **$0.02~0.15** | **$2~15** |

- **主方案**：主流工具走**订阅制**跑 100 题（边际成本为零，但要处理并发限制），另外两个走**国产便宜模型的 API**。现金支出能压到 **¥100~300**。
- **备用方案**：全量实验之前先跑 **30 题 × 3 个 AI 的小规模试跑**，用实测的 token 均值反推全量预算，再决定要不要降到 60 题。
- **底线**：100 题 × 2 个 AI + 30 题 × 第 3 个 AI，报告里标注样本量不同。

## 4.5 "复现公开结果，误差 ≤ 5 个百分点" —— 这个指标必须换一种验证方式

**按字面理解，这个指标没法验证。** 三个各自独立的原因：

**原因一：比较对象对不上。**

公开的数字是针对官方 SWE-bench Verified 那 500 道题的。我们自建的中文题库根本没有任何公开基线可比。

**原因二：统计上做不到。**

假设我们从官方 500 道题里随机抽 50 道来跑。就算某个 AI 的真实解决率正好是 50%，我们抽的这 50 道算出来的比例也会上下浮动——因为抽到哪 50 道是随机的。

统计学上算出来，这个浮动范围大约是 **±14 个百分点**（这叫 95% 置信区间，意思是 100 次抽样里有 95 次会落在这个范围内）。

换句话说：我们量出 36% 和量出 64%，都无法排除"真实值就是 50%"的可能。

抽 100 道，浮动仍有 **±10 个百分点**。要把浮动压到 ±5 个百分点，需要抽将近 **384 道题**。跑 384 道题，时间和钱都不允许。

**原因三：变量控制不住。**

公开结果绑定了特定的模型快照、特定版本的 Agent 框架、特定的提示词。半年后同名模型的行为已经变了，"复现"的自变量根本对不齐。

### 换成三种能证明的验证方式（建议全做，按优先级）

**方案 A —— 重放公开补丁（主方案，强烈推荐）**

思路：某个 AI 的评测结果是公开的，包括**它对每一道题生成的补丁**（SWE-bench 官方的 experiments 仓库里有这些数据）。

我们不重新跑那个 AI，而是**把它已经生成好的补丁拿过来，用我们自己的判定引擎重新判一遍**，然后跟官方公布的"每道题过没过"逐条对比。

- 指标定义：`|我们算出的解决率 − 官方公布的解决率| ≤ 5 个百分点`，同时报告**逐题一致率**（应该达到 98% 以上）。
- **为什么这个能成立**：判定是确定的，不含抽样随机性，也不受模型漂移影响。如果出现偏差，恰恰说明**我们的判定引擎有问题**——而这正是一个评测平台最该验证的东西。
- 成本：**AI 调用费用为零**，只花机器时间。
- 风险：需要能拉到官方镜像。拉不动的话退到方案 A'——用我们自己的官方正确补丁当"必过"的预测集，验证判定引擎不会误判。

**方案 B —— 实跑官方题库子集（辅助证据）**

从官方 Verified 里按仓库分层随机抽 100 道（随机种子固定），用同一个 AI 加同代模型实际跑一遍，报告点估计值和 95% 置信区间，跟公开值比较。

诚实的表述方式：「点估计偏差 X 个百分点，落在抽样误差范围内（±10 个百分点），与公开结果**不矛盾**。」

**方案 C —— 内部一致性（兜底）**

同一个 AI 在同一批题上跑 3 次，报告解决率的标准差（衡量 AI 本身的随机性和平台稳定性）；同一个补丁重判 3 次必须 100% 一致（衡量判定引擎的确定性）。

**答辩时怎么说**：我们没有回避这个指标，而是指出它按字面理解无法验证，并且交付了一个**更强**的验证——直接证明我们的判定引擎和公开评测程序判得一样。

## 4.6 并行度 ≥ 8 和 6 小时

### 并行度：能达标，但要分两层定义

被测 AI 干活的时候，绝大部分时间在等大模型返回，CPU 基本空着。跑测试的时候则是实打实吃 CPU 和内存。

用同一个数字管这两件事，要么浪费吞吐，要么撑爆内存。所以分开设：

```
AGENT_CONCURRENCY   = 8 ~ 12   同时有几个 AI 在干活（受服务商限流约束，不吃本机 CPU）
SANDBOX_CONCURRENCY = 4 ~ 8    同时跑几个测试容器（受 CPU 和内存约束）

对外声明的"并行度" = 同时处于"已开始但还没结束"状态的评测任务数 ≥ 8
```

**本机可用配置（实测宿主 15.7 GB / 24 逻辑核，WSL 被 `.wslconfig` 限为 8C/10G）：**

| 配置 | WSL 资源 | 并发设置 | 说明 |
|:---|:---|:---|:---|
| 当前（未调） | 8 vCPU / 10 GB | `AGENT=8, SANDBOX=4` | 4×1.5G=6G，留 3.7G 给数据库和后端 → 已满足 ≥8 |
| **调整后（已实施并验证）** | **16 vCPU / 11 GB 可用** | **`AGENT=10, SANDBOX=5`** | `memory=12GB` 实际到手 11 GB（WSL 内核开销）；5×1.3G=6.5G，留 4.5G。CPU 从 8→16 只是解除了人为限制 |
| 云主机兜底（可选） | 16 vCPU / 32 GB | `AGENT=12, SANDBOX=8` | 仅最终实验日按小时租用，约 ¥20~50 |

调整方法：编辑 Windows 侧 `%UserProfile%\.wslconfig` 的 `processors=16`、`memory=12GB`，然后在 Windows 执行 `wsl --shutdown` 重启 WSL。**（2026-09-01 已实施并验证：`nproc`=16、`free` 总量 11 GiB。）**
注意：`sandbox_memory_mb` 的默认值应设为 **1280** 而非 1536，以匹配 11 GB 的实际可用量。

配置里已有的 `autoMemoryReclaim=gradual` 会让 WSL 把闲置内存还给 Windows，所以把上限提到 12 GB 并不等于常驻占用 12 GB。

**实测回填（E5-T2，2026-09-06）**：双层并发跑起来了，口径按本节定义实测如下 ——
Oracle × 4 道 Golden 题 × 30 轮 = 120 条作业，`worker_slots=8 / agent=10 / sandbox=5`：

| 指标 | 实测 | 对应要求 |
|:---|:---|:---|
| 在途任务数（= 对外声明的并行度） | 峰值 **8**、时间加权 P50 **8** | MET-03 峰值 ≥8、P50 ≥8 |
| 同时跑的测试容器 | 峰值 **5**、P50 **5** | 正好卡在 `SANDBOX_CONCURRENCY` 上 |
| 同时跑的被测 AI | 峰值 1 | Oracle 不调模型，这一层没排队 |
| 内存峰值 | 28.2%（11.7 GiB 的机器） | 验收线 <80% |

时间序列由 `python -m cli.experiment concurrency --run N --csv` 导出，
算法是拿 `evaluation_task_runs` 的时刻列做扫描线（不采样，见 `07-platform-architecture.md` §15.2.2）。

⚠️ **内存那个数字受题目大小主导，不能直接外推。** Golden 题的测试跑起来只占几十 MB。
按 `sandbox_memory_mb` 的硬上限算最坏情况：5 × 1.5 GB + 3.2 GB 基线 = 91%，超线。
所以本节"默认值应设为 1280"那条建议**必须落实**（5 × 1.25 + 3.2 ≈ 82%，仍偏紧），
或者把 `SANDBOX_CONCURRENCY` 降到 4（4 × 1.5 + 3.2 ≈ 79%）。定档留给 E9-T2 的并发压测。

另建议：**在 WSL 里装原生 docker engine，不要用 Docker Desktop**——后者会额外常驻一个 WSL 发行版和一堆 GUI 进程，在 15.7 GB 的机器上白吃 1~2 GB。

### 6 小时：有条件能达标

详细测算见 §18，这里只给结论。三个必要条件：

1. **镜像必须提前建好。** 否则光装依赖就要 5~15 小时，直接出局。
2. **必须有硬超时。** AI 阶段 12 分钟，测试 8 分钟，单题总计 25 分钟。
3. **外部大模型服务不能成为串行瓶颈。**

- **备用方案**：如果外部限流导致超时，改成**按 AI 分时段跑**（3 个 2 小时的窗口），并且在性能报告里把**平台自己花的时间**和**等外部服务的时间**分开列。这是正确的工程口径——平台的吞吐能力不该为服务商的限流背锅。
- **底线**：如果 300 次还是超 6 小时，就交付"100 题 × 1 个 AI 在 2 小时内跑完"的实测数据 + 推算模型 + 瓶颈分析。

## 4.7 归因准确率 ≥ 85%

**能做到吗：把握较大。** 靠三条设计：

**1. 先用规则分类。** 大约 55~70% 的失败可以直接靠确定性的证据归类：空补丁、语法错误、把别的测试改坏了、超时、AI 工具报错、平台故障。这部分准确率接近 100%，直接把总体拉高。

**2. 让大模型必须引用证据。** 大模型只处理"补丁不空、能跑起来、但目标测试还是没过"这种分不清的情况，而且强制它输出**引用**——必须指出是测试日志的哪一句、补丁的哪一行。不允许自由发挥。`temperature=0`，输出结构化 JSON，置信度低的采样 3 次投票。

**3. 抽检要盲检。** 分层抽样（每类至少 5 例，总共至少 50 例），两人独立标注加第三人裁决，同时报告一致性系数。标注时默认把系统的答案藏起来。

- **备用方案**：如果某两类（典型是"没理解需求"和"修得不完整"）一直分不清，就**合并这两类**，并在报告里说明分类体系的修订过程——这本身就是合格的工程叙述。
