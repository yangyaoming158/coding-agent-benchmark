# 1 Executive Summary（总结）

## 1.1 四周能做完吗

**分开看：平台能做出来，但学校提的六个量化指标不可能全部达标。**

| 要交付的东西 | 四周内能不能做到 | 结论 |
|:---|:---|:---|
| 一个能跑通全流程的评测内核（代码快照 + issue + 验证测试 → AI 改代码 → 收补丁 → 隔离环境跑测试 → 自动判定） | 高 | **能交付** |
| 4 个被测 AI 的接入（Mock / Aider / Claude Code / 自研），再加 1 个国产 CLI | 高 | **能交付** |
| ≥100 道题（中文优先，含国产开源项目） | 中 | **能交付，但必须"自建 + 官方题库"混着来**，全部自建风险太大 |
| 排行榜 / 失败分析 / 人工抽检 / 报告 / 部署文档 | 高 | **能交付** |
| 300 次真实评测（100 题 × 3 个 AI） | 中 | **能做，但主要限制是钱和外部限流**，不是技术 |
| 指标：并行度 ≥ 8 | 中 | **能达标，但要把"并行度"定义清楚**（见 §18） |
| 指标：6 小时跑完 300 次 | 中低 | **只有同时满足"镜像提前建好 + 严格超时 + 机器够用"三个条件才成立** |
| 指标：复现公开结果，误差 ≤ 5 个百分点 | **低（按字面理解根本没法验证）** | **必须换一种验证方法**，理由见 §4.5 |
| 指标：失败归因准确率 ≥ 85% | 中高 | **能达标**，前提是先用规则分类兜底 |

一句话：**能做出一个"小而真"的评测平台，做不出一个"小而全指标达标"的评测平台。**

所以规划的重点不是砍需求，而是给那四个高风险指标每个都设计一条"如果做不到，退到什么程度还算合格"的路线。

## 1.2 最大的四个风险

**1. R00 — 开发环境（学校文档里没有，是实际测出来的）**

已于 2026-09-01 解决。当时的情况是：WSL 里 `docker` 命令不存在；Windows 主机 15.7 GB 内存 / 24 个逻辑处理器，但 WSL 配置文件把它限制成了 8 核 / 10 GB。

学校要求"并行度 ≥ 8"，如果理解成 8 个测试容器同时跑（每个 1 核 2 GB），需要 16 GB 内存，物理上跑不动。

**处理结果**：改配置把 WSL 提到 16 核 / 11 GB（CPU 那部分纯粹是人为限制，改配置就行），装原生 Docker，沙箱的四条限制测试全部通过。**不需要买机器。** 详见 §4.6 和 §10.6。

**2. R10 — 100 道题建不出来**

这是全项目工作量压力最大的一条。

SWE-Bench 原论文的数据是：9 万个 PR 筛出 2294 道题（约 2.5%），后来的 Verified 版本再经人工筛选只留下 500 道（约 22%）。也就是说"自动挖掘 → 真正能用的题"，成功率大概在 0.5%~3% 之间。

要拿到 100 道**验证通过**的题，得筛几千个候选 PR，而且每个候选都要在 Docker 里跑两遍测试才能确认（一次确认修复前失败，一次确认修复后通过），每个 3~10 分钟。

**所以必须第一周就开始，而且要收敛到 8~15 个精选仓库，不能漫无目的地爬整个 GitHub。**

**3. R04 / R08 / R09 — 外部 AI 服务的鉴权、限流和费用**

Claude Code、Codex 这类订阅制的命令行工具，有并发上限，非交互模式下的登录也麻烦。如果按 API 计费，一道真实仓库的题要烧掉 10 万~80 万 token，300 次跑下来可能是**几百美元**。这是学生项目的实际天花板。

**4. R13 — "复现公开结果误差 ≤ 5 个百分点"这个指标没法验证**

公开的数字（比如"某某 AI 在 SWE-bench Verified 上解决率 X%"）是在**官方的 500 道题全集 + 官方镜像 + 官方评测程序 + 特定版本的模型**下得到的。

拿我们自建的中文题库去"复现"它，逻辑上不成立——我们的题库根本没有公开基线。

拿官方题库抽 50 道来复现，统计上也证明不了 ≤5pp（原因见 §4.5，简单说就是抽样误差本身就有 ±14pp）。

## 1.3 最难的三个技术点

**1. 判定要确定，还要防作弊。**

难的不是"跑测试"，而是三件事：

- 测试文件必须由平台强制覆盖。被测 AI 的补丁里，凡是改测试文件的部分都要丢掉。否则它把 `assert` 改成永远成立就"通过"了。
- 必须**逐条**解析测试结果。而且"这条用例在报告里找不到"绝对不能算通过——AI 可能把它删了。
- 工作区里不能有 base commit 之后的 git 历史。否则 AI 一句 `git log origin/main` 就能翻到官方的修复代码。

这三条任何一条漏掉，整个基准就没有可信度了。

**2. 环境要能复现。**

同一道题两周后重跑，必须得出同样的结论。要求：commit 写死、镜像用内容哈希引用、依赖版本锁定、测试命令固定、跑测试时完全断网。

工程上体现为三层镜像结构和环境规格的哈希化。

**3. 吞吐量。**

6 小时目标真正的杀手是**装依赖**。单个仓库 `pip install` 要 60~180 秒，乘以 300 次就是 5~15 小时，光这一项就超预算了。

解法是**按仓库预先构建镜像**，把装依赖的成本从"每次运行都付一遍"变成"每个仓库只付一遍"。

## 1.4 推荐方案

一句话概括：

FastAPI 写的模块化单体（一个代码库，API 和后台 Worker 是两个启动入口）+ 用 PostgreSQL 自带的能力做任务队列（不引入 Redis）+ **两个容器分离的沙箱**（AI 容器可以联网改代码，测试容器从干净镜像重建、完全断网）+ **按仓库预建镜像**保证速度。

接入被测 AI 的协议统一成"标准输入喂 JSON 任务，标准输出返回 JSON 结果（里面带补丁）"，内部允许 AI 直接改文件，对平台只暴露标准化后的补丁。

题库分两套：自建的 `benchmark-cn-v1`（≥100 题，中文优先，含国产开源）作为主交付；官方的 `swebench-verified-subset` 作为校准用（这是唯一能支撑"复现公开结果"这个指标的东西）。

判定 100% 确定，大模型只用于分析失败原因，而且前面先用规则过一遍，能省掉 60% 以上的调用。

第一周必须用**假的 AI（Mock）+ 3~5 道人工造的题**把整条链路跑通，再接真实 AI。
